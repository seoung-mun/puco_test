# 웹 배포 준비 및 멀티플레이 오류 수집 전략 보고서

작성일: 2026-04-06  
관점: Senior Fullstack / MLOps Engineer  
대상: Puerto Rico RL 프로젝트 웹 담당자, 운영 담당자, 연구 팀원

## 1. 보고서 목적

본 문서는 현재 `castone` 코드베이스가 프로젝트 계획서의 웹/시각화 파트를 기준으로 어디까지 구현되어야 하는지 정리하고, 현 시점에서 우선순위를 `배포 후 멀티플레이 오류 수집`에 둘지, 아니면 `추가 구현/검증/보안 강화`에 둘지 판단하기 위해 작성되었다.

핵심 질문은 다음과 같다.

- 웹 담당 코드베이스의 실질적인 완료 기준은 무엇인가?
- 지금 바로 외부 배포를 열고 멀티플레이 환경에서 오류를 수집하는 것이 맞는가?
- 아니라면, 어떤 안정화 작업을 먼저 끝내야 하는가?

## 2. 한 줄 결론

현재 시점에서는 `공개 멀티플레이 배포`보다 `안정화/검증/보안`을 먼저 끝내고, 그 다음 `폐쇄형 알파 배포`로 오류 수집을 시작하는 것이 적절하다.

이유는 단순히 기능이 부족해서가 아니다. 현재 구조는 이미 `게임 UI + 실시간 서버 + RL 엔진 + 운영 로그 + replay + ML 재학습용 transition 로그`까지 연결되어 있어 프로토타입 단계는 지났다. 그러나 멀티플레이 환경에서 수집되는 오류가 `사용자 행위`, `엔진 규칙 드리프트`, `실시간 세션 동기화 문제`, `종료 상태 불일치`, `클라이언트 보안 문제`와 섞일 위험이 아직 크다.

즉, 지금 외부 유저를 넓게 받으면 "유의미한 품질 데이터"가 아니라 "운영 소음"이 더 많이 쌓일 가능성이 높다.

## 3. 현재 코드베이스 상태 요약

현재 저장소는 이미 다음 네 축을 모두 갖추고 있다.

- `frontend/`
  - React + Vite 기반 SPA
  - 로그인, 방 생성/입장, 로비, 실시간 게임 화면, 종료 화면
- `backend/`
  - FastAPI 기반 인증, 방 관리, 게임 진행, WebSocket, 로그 저장
- `PuCo_RL/`
  - 실제 Puerto Rico 규칙 엔진
  - PPO/HPPO 학습 및 평가 코드
- `vis/`
  - DB/JSONL/replay 로그를 사람이 읽을 수 있는 리포트로 변환

즉, 웹 파트의 역할은 더 이상 "보드판을 브라우저에 띄우는 것"이 아니다.  
이 코드베이스는 사실상 아래 역할을 수행해야 한다.

- 인간 대전용 실전 플레이어 인터페이스
- 봇/모델 서빙 연결면
- 멀티플레이 세션 관리자
- 게임 로그 수집기
- replay 검수 도구
- 연구용 데이터 수집 포털

따라서 웹 담당 코드베이스의 완료 기준도 일반 웹앱 기준이 아니라 `운영 가능한 연구 실험 플랫폼` 기준으로 잡아야 한다.

## 4. 웹 코드베이스의 실질적 완료 기준

### 4.1 필수 완료 기준

현재 프로젝트 계획서의 웹 파트에서 반드시 충족해야 하는 기준은 아래와 같다.

1. 인간 플레이어가 3인 게임을 안정적으로 생성, 입장, 시작, 진행, 종료할 수 있어야 한다.
2. 인간 + 봇 혼합 게임에서 턴 진행, reconnect, disconnect, 종료 처리가 일관되어야 한다.
3. 각 게임에 대해 아래 정보가 한 번에 추적 가능해야 한다.
   - `game_id`
   - 플레이어 구성
   - 좌석/시작 위치
   - 사용 모델 버전
   - 종료 사유
   - DB 로그
   - replay 로그
   - JSONL transition 로그
4. 운영자가 특정 게임 한 판을 나중에 재검토할 수 있어야 한다.
5. 오류가 났을 때 `프론트 버그인지`, `백엔드 세션 버그인지`, `엔진 규칙 버그인지`, `모델 행동 문제인지`를 최소한 분류할 수 있어야 한다.

### 4.2 있으면 좋지만 지금은 미뤄도 되는 항목

아래는 공개 서비스 관점에서는 중요할 수 있으나, 현재 연구 일정에서는 우선순위를 낮춰도 된다.

- 공개 매치메이킹
- 랭킹/전적 시스템 고도화
- 관전자 모드
- 리플레이 웹 뷰어 고도화
- 소셜 기능
- 고급 통계 대시보드

현재 단계에서 더 중요한 것은 `예쁜 서비스`가 아니라 `신뢰 가능한 실험 수집기`다.

## 5. 지금 공개 배포보다 안정화가 우선인 이유

### 5.1 백엔드 계약 테스트가 아직 깨져 있음

직접 재현 결과, mayor 관련 계약 테스트가 여전히 실패한다.

- 실행 명령
  - `docker compose exec backend pytest -q tests/test_todo_priority1_task1_mayor_contract.py tests/test_legacy_features.py::TestMayorDistributeErrorFormat::test_slot_capacity_error_returns_400`
- 재현 결과
  - `test_slot_capacity_error_returns_400` 실패
  - 기대값 `400`, 실제값 `200`

이 문제는 단순 테스트 깨짐이 아니라, `엔진/action mask/serializer/legacy contract` 사이의 의미가 어긋나 있음을 뜻한다.  
이 상태에서 실전 플레이 로그를 모으면 규칙 구현 오류와 사용자 오류가 섞여서, 후속 분석 비용이 커진다.

### 5.2 프론트 테스트도 아직 깨져 있음

직접 재현 결과, 프론트 테스트는 `localStorage is not defined`로 실패한다.

- 실행 명령
  - `docker compose exec frontend npm test`
- 재현 결과
  - `vite.config.test.ts` 실패
  - 원인: `frontend/src/i18n.ts`에서 import 시점에 `localStorage` 직접 접근

이 문제는 치명적인 런타임 장애는 아니더라도, 프론트 테스트 신뢰도를 떨어뜨린다.  
즉, UI 수정 이후 회귀 검증이 아직 자동화로 닫혀 있지 않다.

### 5.3 로비 WebSocket 종료 흐름이 위험함

현재 프론트는 `GAME_STARTED`를 받으면 로비 WebSocket을 닫는다.  
문제는 서버 측 로비 WS가 종료 시 `handle_leave()`를 호출하고, 이 로직이 진행 중 게임에서도 플레이어 목록을 수정할 수 있다는 점이다.

이 조합이 위험한 이유는 다음과 같다.

- 정상 게임 시작 직후 참가자가 active room에서 빠지는 현상 가능
- 이후 액션 요청이 참가자 검증에서 막힐 가능성
- 운영 DB 기준 플레이어 목록과 실제 엔진 상태가 어긋날 가능성

이 문제는 멀티플레이 실험에서 매우 고위험이다.  
왜냐하면 유저 입장에서는 "게임 시작은 됐는데 갑자기 내가 플레이어가 아니라고 나오는" 종류의 오류로 보이기 때문이다.

### 5.4 종료 상태와 엔진 상태의 일관성이 약함

현재 disconnect timeout 경로에서는 DB의 `game.status`만 `FINISHED`로 바꾼 뒤 종료 메시지를 브로드캐스트한다.  
그러나 실제 진행 엔진은 `GameService.active_engines`라는 프로세스 메모리 안에 남아 있다.

이 구조에서 생길 수 있는 문제는 아래와 같다.

- DB는 종료됐다고 기록하지만 엔진은 여전히 살아 있음
- 종료 후 액션이 추가로 처리될 가능성
- replay/DB/Redis/실제 게임 진행의 불일치 가능성

연구 관점에서 가장 중요한 것은 한 게임의 로그와 결과가 일관되게 남는 것이다.  
종료 상태가 흔들리면 이후 통계 분석과 인간 대전 로그 해석도 함께 흔들린다.

### 5.5 내부 API 키가 프론트 번들에 들어가는 구조는 공개 배포에 부적합함

현재 프론트는 `VITE_INTERNAL_API_KEY`를 빌드 타임에 주입받고, 일부 레거시 write endpoint 호출 시 `X-API-Key` 헤더에 자동으로 넣는다.

이는 개발/과도기 구조로는 이해할 수 있으나, 외부 공개 범위를 넓히기 전에 반드시 제거하거나 서버 측 계약으로 옮겨야 한다.  
브라우저 번들에 들어간 키는 사실상 비밀이 아니기 때문이다.

즉, `internal`이라는 이름을 쓰고 있지만 실제 공개 정적 번들에 포함되는 순간 더 이상 내부 키가 아니다.

## 6. Senior Fullstack 관점 권고

### 6.1 지금 필요한 것은 기능 추가보다 상태 관리의 신뢰성 확보

현재 시스템은 화면 수나 기능 수가 적어서 문제가 생기는 것이 아니다.  
문제는 상태가 여러 층에 분산되어 있다는 점이다.

- 프론트 로컬 상태
- WebSocket 연결 상태
- 백엔드 메모리 엔진 상태
- PostgreSQL 정본 메타데이터
- Redis 실시간 메타
- 파일 로그

이 구조에서 시니어 풀스택 관점의 최우선 과제는 아래 두 가지다.

1. 상태 전이 계약을 명시적으로 정리할 것
2. 세션 생명주기별 불변 조건을 테스트로 고정할 것

예를 들면 다음과 같은 질문에 코드가 즉시 답할 수 있어야 한다.

- 게임 시작 직후 플레이어는 어떤 저장소에서 어떤 상태가 되어야 하는가?
- 플레이어가 로비에서 게임 화면으로 전환할 때 leave로 간주되는가, 전환으로 간주되는가?
- disconnect timeout 후 액션 요청은 무조건 차단되는가?
- 종료 이후 replay와 DB 결과는 언제, 어떤 순서로 finalize되는가?

### 6.2 웹 파트의 P0는 "운영 가능한 멀티플레이 흐름"이다

지금 가장 중요한 웹 개발 목표는 다음과 같다.

- 방 생성/입장/대기/시작
- 게임 시작 후 플레이어 유지
- 실시간 상태 반영
- reconnect/disconnect 처리
- 종료 후 결과 조회
- replay/로그 검수

이 여섯 가지가 닫히기 전에는, UI를 더 예쁘게 하거나 관리 화면을 늘리는 것보다 멀티플레이 상태 머신을 먼저 다듬는 편이 훨씬 가치가 크다.

## 7. MLOps Engineer 관점 권고

### 7.1 지금 수집해야 하는 것은 "많은 로그"가 아니라 "신뢰 가능한 로그"

이 프로젝트의 웹 시스템은 단순 게임 서비스가 아니라 RL 데이터 수집 파이프라인의 앞단이다.  
따라서 오류 수집과 게임 로그 수집의 품질 기준은 일반 서비스보다 더 엄격해야 한다.

지금 가장 중요한 것은 아래 항목이 한 게임 단위로 완전히 연결되는 것이다.

- 입력한 유저/봇 구성
- 좌석 위치
- 모델 artifact 정보
- action mask/phase 정보
- state transition
- 종료 사유
- 최종 점수
- replay 검수 가능 여부

이 중 하나라도 흔들리면 다음 문제가 생긴다.

- 인간 대전 데이터를 재학습에 넣기 어렵다
- 모델 비교 결과를 신뢰하기 어렵다
- 밸런스 검증 시 데이터 클린징 비용이 커진다
- 같은 오류가 FE/BE/엔진 중 어디서 발생했는지 분리하기 어려워진다

### 7.2 공개 배포보다 폐쇄형 알파가 더 적합함

지금 단계에서는 다음 순서가 합리적이다.

1. 내부 개발자/팀원 중심 도그푸드
2. 소수 초대 기반 폐쇄형 알파
3. 로그/리플레이/종료 사유 분류 체계 안정화
4. 그 이후 외부 범위 확대

즉, `많은 유저`보다 `잘 설명 가능한 소수의 게임 로그`가 더 가치 있다.

### 7.3 오류 수집 체계는 배포 전에 최소한 이 정도는 있어야 함

배포 전에 다음 정보가 자동으로 남아야 한다.

- 프론트 build/version 식별자
- 백엔드 build/version 식별자
- 사용 중인 모델 artifact 이름
- game_id
- player_id / actor_type
- 종료 사유
- disconnect 여부
- 예외 stack trace
- replay 파일 경로
- jsonl 파일 경로

현재 구조는 일부를 이미 갖고 있지만, 운영에서 바로 분류 가능한 수준으로 묶는 작업은 더 필요하다.

## 8. 지금 무엇을 먼저 해야 하는가

### 8.1 추천 우선순위

현재 우선순위는 아래 순서가 가장 적절하다.

#### P0. 공개 배포 blocker 제거

- mayor 계약 드리프트 수정
- 프론트 `i18n` 테스트 안정화
- 로비 WS 종료가 leave로 처리되는 경로 수정
- 종료 후 액션 차단 보장
- 브라우저 번들에 들어가는 internal key 제거 또는 대체

#### P1. 운영 관측성 강화

- FE/BE 공통 request/game correlation id
- disconnect / reconnect / timeout 사유 구조화
- game-level error summary 생성
- 운영자가 한 게임을 끝까지 추적할 수 있는 관리자 보고 흐름 정리

#### P2. 폐쇄형 알파 배포

- 내부 팀원 + 지인 대상
- 정해진 시간대에만 플레이
- 오류 리포트 템플릿 제공
- 종료 직후 replay/DB/jsonl 검수

#### P3. 그 이후 기능 확장

- 리플레이 웹 UI 고도화
- 통계 대시보드
- 사람 대전 데이터 태깅 보조
- 연구용 분석 페이지

## 9. "지금 배포하면서 오류를 모을까?"에 대한 최종 판단

질문에 대한 직접적인 답은 다음과 같다.

### 답변

`지금 바로 외부에 넓게 배포해서 멀티플레이 오류를 수집하는 것`은 권장하지 않는다.  
대신 `안정화와 보안을 먼저 진행한 뒤, 제한된 사용자만 받는 폐쇄형 알파`를 여는 것은 권장한다.

즉, 선택지는 아래 둘 중 하나가 아니라,

- 배포해서 오류를 모은다
- 배포하지 않고 계속 개발한다

가 아니라 아래처럼 보는 것이 더 정확하다.

1. 먼저 운영 사고를 만드는 구조적 blocker를 닫는다.
2. 이후 로그 품질이 보장되는 작은 배포를 연다.
3. 그 배포에서 수집한 데이터를 기반으로 다음 단계를 넓힌다.

이 전략이 연구 일정과 개발 현실 모두에 더 잘 맞는다.

## 11. 최종 정리

현재 웹 코드베이스는 "무엇을 더 만들어야 할지 모르는 초기 상태"가 아니라, "무엇을 덜 벌리고 무엇을 먼저 닫아야 하는지 선택해야 하는 상태"에 가깝다.

이미 충분히 많은 기능은 있다.  
이제 중요한 것은 아래 세 가지다.

- 멀티플레이 세션의 상태 일관성
- 종료/오류/재연결 시나리오의 검증 가능성
- 수집되는 게임 로그의 연구용 신뢰성

따라서 현 시점의 가장 좋은 전략은 다음과 같다.

- 공개 배포는 잠시 미루기
- 구조적 blocker를 먼저 제거하기
- 그 다음 폐쇄형 알파로 오류를 수집하기
- 수집된 로그가 연구 데이터로도 쓸 수 있는 수준인지 확인하기

이 기준을 만족하면, 그때부터 웹 코드베이스는 단순한 데모가 아니라 `실전용 인간 대전 + 연구용 로그 수집 플랫폼`으로 볼 수 있다.
